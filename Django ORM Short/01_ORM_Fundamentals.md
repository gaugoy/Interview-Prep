## Q1. (Easy) How does Django QuerySet lazy evaluation work internally?
**Answer:** Building a QuerySet (`filter`, `exclude`, `order_by`…) doesn't touch the database — each call just returns a new QuerySet with an updated internal `Query` object. SQL is generated and run only when you actually need the results (iteration, `list()`, `len()`…). Results are then stored in the QuerySet's `_result_cache`. This lets you build queries step by step and run one final query.

---

<a name="q2"></a>
## Q2. (Easy) What are the database evaluation triggers for a QuerySet?
**Answer:** A QuerySet hits the DB when you:
- iterate it (`for x in qs`), call `list()`, `len()`, `bool()` / `if qs:`
- slice with a step (`qs[::2]`) or index it (`qs[0]`)
- call `repr()` (shell prints first 20 rows), pickle it, or use `x in qs`
Methods that always run a query immediately: `get()`, `first()`, `last()`, `count()`, `exists()`, `aggregate()`, `update()`, `delete()`, `create()`.

---

<a name="q3"></a>
## Q3. (Easy) How does QuerySet slicing affect database queries?
**Answer:** Slicing an unevaluated QuerySet is still lazy and becomes `LIMIT/OFFSET`: `qs[10:20]` → `LIMIT 10 OFFSET 10`. `qs[0]` runs `LIMIT 1` immediately (raises `IndexError` if empty). A step (`qs[::2]`) forces evaluation. Negative indexing isn't supported. After slicing you can't `filter()` any more (`TypeError`).

---

<a name="q4"></a>
## Q4. (Easy) Explain the QuerySet caching mechanism and when it is bypassed.
**Answer:** When a QuerySet is evaluated, its rows are stored in `_result_cache`; iterating the **same** QuerySet object again uses the cache, no new query.
Bypassed when:
- you create a new QuerySet (`qs.filter(...)`, `qs.all()`, `Model.objects.filter(...)` again)
- you index/slice an **unevaluated** QuerySet (`qs[0]` runs a query, doesn't fill the cache)
- you use `iterator()` (no caching at all)
- you call `count()`/`exists()` on an unevaluated QuerySet

```python
qs = Book.objects.all()
[b.title for b in qs]   # query
[b.price for b in qs]   # cache — no query
```

<a name="q5"></a>
## Q5. (Medium) How does Django compile a QuerySet to SQL?
**Answer:** The QuerySet holds a `Query` object (a tree of tables, joins, where-conditions, ordering, limits). On evaluation, Django gets a backend-specific **SQL compiler** for it, which walks the tree and produces an SQL string with `%s` placeholders plus a separate list of params. The DB driver then sends them to the database. Because the compiler is per backend, the same QuerySet gives correct SQL for PostgreSQL, MySQL, SQL Server, etc.

---

<a name="q6"></a>
## Q6. (Easy) What is the impact of checking boolean values on querysets (if queryset:) vs (if queryset.exists())?
**Answer:** `if qs:` evaluates the whole QuerySet (fetches all rows) and caches them. `if qs.exists():` runs a cheap `SELECT 1 ... LIMIT 1` and loads nothing.
- Only need yes/no → `exists()`.
- Will use the rows right after → `if qs:` is fine (one query, rows reused from the cache); `exists()` + loop would be 2 queries.

---

<a name="q7"></a>
## Q7. (Medium) How does Django handle database connection pooling and connection lifetime (CONN_MAX_AGE)?
**Answer:** By default (`CONN_MAX_AGE = 0`) Django opens a connection per request and closes it at the end. `CONN_MAX_AGE = 60` keeps the connection open for reuse for 60 s (**persistent connections**, one per thread/worker) — that's not a real pool. `CONN_HEALTH_CHECKS = True` checks a reused connection before the request uses it.
Real pooling: Django 5.1+ supports a native PostgreSQL pool (`"OPTIONS": {"pool": True}`, psycopg 3), or an external pooler like **PgBouncer**.

```python
DATABASES["default"]["CONN_MAX_AGE"] = 60
DATABASES["default"]["CONN_HEALTH_CHECKS"] = True
```

<a name="q8"></a>
## Q8. (Easy) What is the difference between QuerySet.iterator() and normal QuerySet evaluation?
**Answer:** Normal evaluation loads **all** rows into memory and caches them on the QuerySet. `iterator()` streams rows in chunks and **doesn't cache**, so memory stays low — good for processing large tables once. On PostgreSQL it uses a server-side cursor; `chunk_size` (default 2000) controls how many rows are fetched at a time.

```python
for row in Log.objects.filter(level="error").iterator(chunk_size=5000):
    process(row)
```

---

<a name="q9"></a>
## Q9. (Medium) When does iterator() make multiple queries under the hood?
**Answer:**
- With `prefetch_related` + `chunk_size` (Django 4.1+): one prefetch query **per chunk** for each relation.
- Accessing deferred fields or un-prefetched relations inside the loop → extra queries per row (N+1).
- The main query is still one SQL statement; on PostgreSQL rows are fetched in several round-trips from the server-side cursor.
**Gotcha:** with PgBouncer in transaction pooling mode, server-side cursors break — set `DISABLE_SERVER_SIDE_CURSORS = True`.

---

<a name="q10"></a>
## Q10. (Medium) How does Django manage cursor connections internally?
**Answer:** Each database alias has a `DatabaseWrapper` per thread. When a query runs, Django calls `connection.cursor()`, which first ensures a real DB connection exists (connecting lazily if needed), then returns a wrapped cursor that executes SQL with params, handles errors, and (in debug) logs queries. Cursors are short-lived and closed after use; the connection itself lives until the request ends or `CONN_MAX_AGE` expires.

---

<a name="q11"></a>
## Q11. (Easy) How do you inspect the SQL generated by a Django QuerySet?
**Answer:**
- `print(qs.query)` — approximate SQL (params inlined, not exact quoting).
- `qs.explain()` — the DB execution plan.
- `connection.queries` — executed queries (only with `DEBUG=True`).
- `CaptureQueriesContext` in tests, django-debug-toolbar in dev, or log the `django.db.backends` logger.

---

<a name="q12"></a>
## Q12. (Easy) What is the difference between list(queryset) and queryset.all()?
**Answer:** `list(qs)` **evaluates** the QuerySet and returns a Python list of objects. `qs.all()` returns a **new, unevaluated QuerySet** (a copy) — no query yet. `all()` is handy to get fresh data from an already-evaluated QuerySet, since the copy doesn't share the old cache.

---

<a name="q13"></a>
## Q13. (Medium) How does Django ORM map database-specific data types to Python types?
**Answer:** Each backend has a mapping of model fields to column types (e.g. `CharField` → `varchar`, `JSONField` → `jsonb` on PostgreSQL). On the way in, a field's `get_prep_value()` / `get_db_prep_value()` converts Python values for the DB; on the way out, the driver returns basic types and the field's `from_db_value()` / backend converters turn them into Python objects (`Decimal`, timezone-aware `datetime`, dicts for JSON). Custom fields override these methods.

---

<a name="q14"></a>
## Q14. (Medium) How does Django's lazy database connection establishment work?
**Answer:** Django doesn't connect at startup. `connections["default"]` creates a wrapper object only; the actual network connection is opened the first time a query needs a cursor (`ensure_connection()`). So requests that never touch the DB never open a connection, and each thread opens its own connection on first use.

---

<a name="q15"></a>
## Q15. (Easy) What are the performance costs of QuerySet chaining?
**Answer:** Chaining (`.filter().exclude().order_by()`) only clones the Python `Query` object each time — small CPU cost, no DB cost. SQL is built and run once on evaluation. Real costs come from what you chain: extra JOINs from filters across relations (separate `.filter()` calls on multi-valued relations can add extra joins), and rebuilding querysets inside loops.

---

<a name="q16"></a>
## Q16. (Medium) How does the ORM handle query caching across different application threads?
**Answer:** It doesn't — there's **no shared query cache** in the ORM. The only cache is the `_result_cache` of a single QuerySet object, living in that object's memory. Each thread/request builds its own QuerySets and its own DB connection. For cross-request caching use Django's cache framework (Redis/Memcached). Avoid sharing one QuerySet object between threads.

---

<a name="q17"></a>
## Q17. (Medium) Explain the role of django.db.connection in multi-threaded environments.
**Answer:** `django.db.connection` is a proxy to the **current thread's** connection for the `default` alias (`connections["default"]`). Every thread gets its own connection object — connections are never shared across threads. In your own threads (background workers, `ThreadPoolExecutor`), Django won't clean up for you: call `connection.close()` (or `close_old_connections()`) when the thread finishes, otherwise connections leak.

---

<a name="q18"></a>
## Q18. (Easy) What is the difference between QuerySet cloning and evaluation?
**Answer:** **Cloning** = every chain method returns a new QuerySet with a copied `Query`; no SQL runs and the original is unchanged. **Evaluation** = the SQL actually runs and results are stored in `_result_cache`. Clones never share the cache of the original.

---

<a name="q19"></a>
## Q19. (Easy) How do you run raw SQL queries using Manager.raw()?
**Answer:** `Model.objects.raw(sql, params)` runs your SELECT and maps each row to a model instance. The query must include the **primary key**; columns are matched to fields by name (use aliases or `translations=` if names differ).

```python
people = Person.objects.raw("SELECT id, first_name FROM app_person WHERE last_name = %s", ["Smith"])
for p in people:
    print(p.first_name)
```

---

<a name="q20"></a>
## Q20. (Easy) What are the limitations of Manager.raw() compared to normal QuerySets?
**Answer:** A `RawQuerySet` can't be chained — no `filter()`, `exclude()`, `annotate()`, `select_related()`; it bypasses custom manager filters; SQL is backend-specific; columns you didn't select are deferred (accessing them = extra query per row); only SELECT queries are allowed. For anything else use `connection.cursor()`.

---

<a name="q21"></a>
## Q21. (Easy) How does Django prevent SQL injection when using raw queries?
**Answer:** By passing values **separately** as params: `raw(sql, [value])` / `cursor.execute(sql, [value])`. The DB driver binds them safely, so user input is never treated as SQL. It only protects you if you use params — formatting values into the SQL string (f-strings, `%`) is still injectable. Table/column names can't be params, so whitelist them.

---

<a name="q22"></a>
## Q22. (Easy) How do you execute custom SQL using connection.cursor()?
**Answer:** For queries that don't map to a model (reports, updates, DB-specific features):

```python
from django.db import connection

with connection.cursor() as cursor:
    cursor.execute("UPDATE app_book SET stock = stock - 1 WHERE id = %s", [book_id])
    cursor.execute("SELECT status, COUNT(*) FROM app_order GROUP BY status")
    rows = cursor.fetchall()      # list of tuples
```
Use `connections["other"].cursor()` for another database alias.

<a name="q23"></a>
## Q23. (Medium) What is the lifecycle of a database query in Django?
**Answer:**
1. Build the QuerySet (lazy, just a `Query` object).
2. Evaluation triggers it.
3. The compiler turns `Query` into SQL + params.
4. `connection.cursor()` (connects if needed) executes it inside the current transaction/autocommit.
5. Rows are fetched, converted to Python types, built into model instances (or dicts/tuples).
6. Results are cached on the QuerySet.
7. At request end, the connection is closed or kept per `CONN_MAX_AGE`.

---

<a name="q24"></a>
## Q24. (Medium) How does the ORM handle connection dropouts or database disconnects?
**Answer:** Django does **not** retry a failed query — you get `OperationalError` / `InterfaceError`. At the start and end of each request it closes connections that are broken or past `CONN_MAX_AGE`, and with `CONN_HEALTH_CHECKS = True` it tests a reused connection before use. In long-running processes (Celery, cron, management commands) call `close_old_connections()` periodically so a dead connection is replaced. If the error happens inside `atomic()`, the transaction is rolled back.

<a name="q25"></a>
## Q25. (Medium) Explain Django 5.0's support for asynchronous QuerySet methods (e.g. aexists(), acount()).
**Answer:** Since Django 4.1, QuerySets have async versions of methods that hit the DB: `aget()`, `afirst()`, `acount()`, `aexists()`, `acreate()`, `aupdate()`, `adelete()`, and `async for obj in qs`. Lazy methods (`filter`, `order_by`) stay normal.

```python
async def view(request):
    count = await Book.objects.filter(active=True).acount()
    async for b in Book.objects.filter(active=True):
        ...
```
**Gotcha:** under the hood the DB call still runs in a thread (no fully async driver yet), and `transaction.atomic()` doesn't work in async code — wrap transactional code with `sync_to_async`.

---

<a name="q26"></a>
## Q26. (Medium) How does the query cache handle slice modifications internally?
**Answer:** If the QuerySet is **already evaluated**, slicing/indexing just slices the cached Python list — no query. If it's **not evaluated**, slicing returns a new QuerySet with LIMIT/OFFSET set (lazy), and indexing runs a `LIMIT 1` query without filling the original's cache.

```python
qs = Book.objects.all()
qs[0]          # query (LIMIT 1)
list(qs)       # query, fills cache
qs[0]          # from cache, no query
```

<a name="q27"></a>
## Q27. (Hard) What is the internal design of django.db.models.query.QuerySet?
**Answer:** A QuerySet is a lazy wrapper with a few key attributes:
- `model` and `query` — the `sql.Query` object describing the SQL (tables, joins, where tree, ordering, limits).
- `_db` — which database alias to use.
- `_result_cache` — the rows once evaluated.
- `_prefetch_related_lookups` — pending prefetches.
- `_iterable_class` — how rows become objects (`ModelIterable`, `ValuesIterable`…).
Chain methods clone it (`_chain()`); evaluation (`_fetch_all()`) runs the query. Managers (`objects`) just create and proxy to QuerySets.

---

<a name="q28"></a>
## Q28. (Hard) How does Django compile filter parameters into SQL parameters?
**Answer:** `filter(price__gte=10)` is split into a field (`price`) and a lookup (`gte`). Django resolves the field (adding joins for `a__b` paths), creates a lookup object (`GreaterThanOrEqual`) and adds it to the WHERE tree. At compile time each lookup's `as_sql()` returns SQL with a placeholder and the prepared value: `('"price" >= %s', [10])`. Values are converted with the field's `get_db_prep_value()`, and the driver binds them — values never go into the SQL string.

---

<a name="q29"></a>
## Q29. (Hard) What is the compile time overhead of complex querysets in Python?
**Answer:** Building and compiling a query costs Python CPU — usually tiny, but complex querysets (many annotations, subqueries, big `Q` trees) can take noticeable time, which matters if you build them inside loops or on very hot endpoints. Reduce it by building the queryset once instead of per item, avoiding queries in loops, and for a few extremely hot complex queries, using raw SQL. Measure with a profiler before optimising.

---

<a name="q30"></a>
## Q30. (Medium) How does Django handle raw queries in multi-database environments?
**Answer:** `Manager.raw()` picks the database through the router (`db_for_read`); force one with `Model.objects.using("replica").raw(...)` or `.raw(...).using("replica")`. `connection.cursor()` always uses `default` — for other databases use `connections["alias"].cursor()`. Remember the SQL dialect must match that database (e.g. PostgreSQL vs SQL Server).

---

<a name="q31"></a>
## Q31. (Hard) Explain the connection validation wrapper in database backend drivers.
**Answer:** Before reusing a persistent/pooled connection, it should be validated so a request doesn't fail on a dead socket. In Django, `CONN_HEALTH_CHECKS = True` makes the backend call `is_usable()` (a cheap check, e.g. `SELECT 1`) the first time a reused connection is used in a request; broken or expired connections are closed and reopened. Pools (psycopg pool, PgBouncer) have their own checks/timeouts. Without validation you see intermittent "connection already closed" errors.

---

<a name="q32"></a>
## Q32. (Medium) How does connection.close() affect connection pools?
**Answer:** Depends on what's underneath:
- Plain/persistent connections → closes the real DB connection; the next query opens a new one.
- Django 5.1 PostgreSQL pool → returns the connection to the pool.
- PgBouncer → closes the client connection to PgBouncer; PgBouncer keeps its server connection for reuse.
Don't call it inside an `atomic()` block; do call it at the end of your own threads/scripts.

---

<a name="q33"></a>
## Q33. (Medium) How do async QuerySet methods interact with WSGI servers?
**Answer:** Under WSGI each request is handled by a sync worker. An async view still works — Django runs it in an event loop for that request — but you gain no concurrency, and async ORM calls still run the DB work in a thread. To get real benefits from async views (many concurrent slow I/O calls), run under ASGI (Uvicorn/Daphne).

---

<a name="q34"></a>
## Q34. (Medium) What is the role of the database driver backend layer?
**Answer:** `django.db.backends.<vendor>` adapts the ORM to a specific database. Main pieces:
- `DatabaseWrapper` — connection management (uses the DB-API driver: psycopg, mysqlclient, pyodbc for `mssql-django`).
- `DatabaseOperations` — dialect details (quoting, date functions, limits).
- `DatabaseFeatures` — capability flags (e.g. supports `RETURNING`).
- `SchemaEditor` — DDL for migrations; plus introspection and test-DB creation.

---

<a name="q35"></a>
## Q35. (Hard) How do you write custom SQL compilers for custom backends?
**Answer:** A backend points `DatabaseOperations.compiler_module` to a module with subclasses of `SQLCompiler`, `SQLInsertCompiler`, etc.; you override `as_sql()` to change generated SQL (e.g. SQL Server's `TOP` / `OFFSET FETCH` — that's what `mssql-django` does). It's rarely needed: for one function or lookup, define a custom `Func`/`Lookup` with an `as_<vendor>()` method (e.g. `as_postgresql`) instead of a whole compiler.
