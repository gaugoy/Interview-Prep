<a name="q1"></a>
## Q1. (Hard) Design ORM strategy for 500M rows.
**Answer:**
1. Know the access patterns; index exactly for them (composite, partial, covering).
2. Partition by time (or tenant); filter on the partition key; retention = drop partitions.
3. Keyset pagination only; no unbounded queries or full `COUNT(*)`.
4. Select only needed columns; no N+1; batch all writes.
5. Summary tables / materialized views for dashboards; replicas + cache for reads.
6. Archive cold data; monitor with `pg_stat_statements`.

<a name="q2"></a>
## Q2. (Hard) How would you eliminate N+1 queries across microservices?
**Answer:** Across services the N+1 becomes N HTTP calls. Fix: batch APIs (`GET /users?ids=1,2,3`), a data loader that collects ids and calls once per request, local read-models/caches of the other service's data kept in sync by events, or an API gateway/BFF that composes responses. Add per-request call-count monitoring.

---

<a name="q3"></a>
## Q3. (Hard) How would you migrate a 2TB table with zero downtime?
**Answer:**
1. Create the new table/structure alongside the old one.
2. Dual-write (app or trigger) so new changes go to both.
3. Backfill old data in throttled batches (or logical replication).
4. Verify counts/checksums.
5. Switch reads, then writes, behind a feature flag.
6. Keep the old table for rollback, then drop it.
Never run a rewriting `ALTER` on a 2TB table in place.

<a name="q4"></a>
## Q4. (Medium) How would you implement audit logging?
**Answer:** Decide what's needed (who, what, when, old/new values). Options: django-simple-history/auditlog for app-level history (has the user, misses bulk/raw SQL), DB triggers or CDC for complete capture (pass the user id via `SET LOCAL`). Store audit data append-only, partition by time, and keep it out of the hot tables.

<a name="q5"></a>
## Q5. (Hard) How would you design multi-tenant architecture?
**Answer:** Choose isolation by needs: shared tables + `tenant_id` (most scalable; enforce scoping in a base manager/middleware, tenant-leading indexes, maybe row-level security), schema per tenant (stronger isolation, heavier migrations), or DB per tenant (strongest, for few big/regulated tenants). Resolve the tenant per request (domain/token), and test that cross-tenant access is impossible.

---

<a name="q6"></a>
## Q6. (Medium) How would you scale read-heavy workloads?
**Answer:** In order: fix queries and indexes → cache hot data (Redis, with invalidation and stampede protection) → read replicas via a router (handle replication lag) → pre-computed read models (summary tables, materialized views, search index) → CDN/HTTP caching for public responses.

---

<a name="q7"></a>
## Q7. (Hard) How would you handle distributed transactions?
**Answer:** Avoid 2-phase commit. Use the **saga** pattern (each step commits locally; failures trigger compensating actions) and the **outbox** pattern for reliable events, with idempotent consumers and retries. Design for eventual consistency and make the state visible (e.g. order status "pending payment").

---

<a name="q8"></a>
## Q8. (Medium) How would you identify ORM bottlenecks in production?
**Answer:** APM traces per endpoint (DB time vs total, queries per request) → `pg_stat_statements` for the costliest queries → slow-query logs/`auto_explain` for plans → reproduce on staging with `EXPLAIN ANALYZE` → fix (N+1, indexes, pagination) → add query-count tests so it doesn't come back.

---

<a name="q9"></a>
## Q9. (Medium) How would you debug slow PostgreSQL queries generated by Django ORM?
**Answer:** Get the exact SQL (`str(qs.query)`, logs), run `EXPLAIN (ANALYZE, BUFFERS)`, and look for seq scans on big tables, bad row estimates (run `ANALYZE`), sorts spilling to disk, and row explosion from joins. Then add/adjust indexes, rewrite the queryset (Exists instead of join + distinct, fewer columns), or pre-aggregate.

---

<a name="q10"></a>
## Q10. (Medium) When should ORM be replaced by raw SQL?
**Answer:** When the ORM can't express the query (recursive CTEs, LATERAL, complex window frames, DB-specific features), when a measured hot query needs hand-tuned SQL, or for bulk operations like `COPY`/`MERGE`. Keep raw SQL parameterised, isolated in one place, and tested. Not for normal CRUD.

---

<a name="q11"></a>
## Q11. (Hard) How would you design database strategy for multi-region active-active deployment in Django?
**Answer:** Prefer partitioning data **by region/tenant** so each record has one home region that accepts its writes, with replicas elsewhere for reads. True multi-master writes on the same rows need conflict resolution — use a distributed SQL database (CockroachDB, Spanner-like) or design conflict-free data. Use globally unique ids (UUID), and route users to their home region.

---

<a name="q12"></a>
## Q12. (Hard) How would you handle real-time inventory reservation system concurrency under peak load?
**Answer:** Make the decrement atomic: `Item.objects.filter(pk=pk, stock__gte=qty).update(stock=F("stock") - qty)` — returns 0 if not enough stock, no lock held across the request. Create reservations with an expiry and release expired ones in a job. For extreme hot items, use a Redis counter (atomic `DECRBY`) in front of the DB, or a queue that serializes orders per item.

---

<a name="q13"></a>
## Q13. (Hard) How would you implement secure database-level column-encryption transparently to Django models?
**Answer:** A custom field that encrypts in `get_prep_value()` and decrypts in `from_db_value()` (keys from a KMS/vault, with key ids stored for rotation), or PostgreSQL `pgcrypto` / DB-native encryption. Encrypted columns can't be filtered/indexed — add a hashed lookup column if you need equality search. Also mask them in logs and admin.

---

<a name="q14"></a>
## Q14. (Hard) How would you structure a safe migration path from a monolithic database to microservice databases?
**Answer:** Strangler approach: pick one bounded context, stop other modules from touching its tables directly (go through a service/API), copy its data to the new database and keep it in sync (dual-write or CDC), switch reads then writes to the new service, then remove the old tables. Repeat per domain; replace cross-domain joins with APIs or read-models.

---

<a name="q15"></a>
## Q15. (Hard) How would you manage schema migrations for a high-availability Django app with 15-minute deployment cycles?
**Answer:** Every migration must be backward compatible with the currently running code (expand/contract). Run migrations as a separate step before rolling out code, keep them small and fast, use concurrent index creation and `lock_timeout`, move backfills to background jobs, and check migrations in CI (`makemigrations --check`, SQL review for locking operations).

---

<a name="q16"></a>
## Q16. (Medium) How would you design rate-limiting at the database layer vs. distributed cache layer?
**Answer:** Redis (or an API gateway) is the right place for request-rate limiting: atomic increments with TTL, very fast, shared across servers. The database is for **durable** quotas (monthly API usage, billing limits) where accuracy and history matter — updated in batches, not on every request.

---

<a name="q17"></a>
## Q17. (Medium) How would you handle schema evolution for JSONFields storing flexible semi-structured user data?
**Answer:** Add a `schema_version` key, validate the JSON with a schema/Pydantic model on write, read old versions with backward-compatible code (or migrate them lazily on read/write or with a batch job). Promote frequently queried keys to real columns (or GeneratedFields) with indexes.

---

<a name="q18"></a>
## Q18. (Hard) How would you scale file/image metadata querying on a platform processing 100M uploads daily?
**Answer:** Store files in object storage; store compact metadata in a table partitioned by time (and maybe tenant), insert in batches (`COPY`/buffered writes via a queue), index only real query patterns, and push search/filtering by many attributes to a search engine. Old partitions go to cheaper storage/archive.

---

<a name="q19"></a>
## Q19. (Hard) How would you handle double-entry accounting ledger consistency in Django ORM?
**Answer:** Each transaction creates balanced entries (debits = credits) in one `atomic()` block; ledger entries are append-only (corrections are new reversing entries); amounts are `DecimalField`; lock or atomically update account balances; add DB constraints (non-zero amounts, idempotency key unique) and a periodic reconciliation job that checks every journal sums to zero.

---

<a name="q20"></a>
## Q20. (Hard) How would you implement database tenancy routing for 5,000 corporate clients with isolated databases?
**Answer:** A tenant registry (tenant → DB connection info) cached in memory; middleware resolves the tenant and sets the alias in a context variable; a router returns it; connection settings are added to `connections.databases` lazily. Use a pooler per DB cluster (not 5,000 persistent connections per worker), run migrations per tenant with a parallel job, and monitor per-tenant failures. Group small tenants on shared clusters.

---

<a name="q21"></a>
## Q21. (Hard) How would you prevent database connection starvation during sudden traffic spikes?
**Answer:** Put a pooler in front (PgBouncer) with fixed server connections; set statement and lock timeouts so slow queries free connections; keep transactions short; cache aggressively; rate-limit/shed load at the edge; and size web + worker concurrency so their total connections can't exceed the DB limit.

---

<a name="q22"></a>
## Q22. (Medium) How would you scale search indexing updates from Django ORM without blocking primary transactions?
**Answer:** Don't index inside the request/transaction. After commit (`on_commit`) or via an outbox table, queue the object ids; a worker loads them in batches and sends bulk updates to Elasticsearch. Debounce repeated updates of the same object, and keep a full re-index job for recovery.

---

<a name="q23"></a>
## Q23. (Hard) How would you implement automated read-replica failover fallback in Django database routers?
**Answer:** A background health check (or cached check every few seconds) tracks replica availability and lag; the router's `db_for_read` returns a healthy replica, falling back to the primary when none are healthy. Combine with connection timeouts so a dead replica fails fast. Primary failover itself is handled by the DB platform/proxy.

---

<a name="q24"></a>
## Q24. (Hard) How would you design a data archiving job that deletes 50M rows daily from production tables with zero performance impact?
**Answer:** Best: partition by day and **drop/detach** whole partitions — no row deletes at all. Without partitions: delete in small PK batches (thousands of rows), each in its own short transaction, throttled based on replica lag, during off-peak hours, with FK indexes in place and fast-delete (no signals). Copy to the archive first if data must be kept.

---

<a name="q25"></a>
## Q25. (Medium) How does Django 5.0's GeneratedField optimize complex real-time scoring algorithms directly in PostgreSQL?
**Answer:** If the score is a deterministic formula over columns of the same row, a stored `GeneratedField` computes it on every write, so reads can filter/sort/index by score instantly without per-query calculation. It can't use other tables, aggregates or time-dependent values — for those, compute in a job or trigger and store the result.

---

<a name="q26"></a>
## Q26. (Hard) How would you design GDPR right-to-be-forgotten cleanups on tables with complex FK relations?
**Answer:** Maintain a map of every model holding personal data and the rule per model (delete vs anonymize). Process the user in one transaction: anonymize records that must be kept (orders, invoices, audit), delete the rest in dependency order, then clean caches, search indexes and files. Run it as a tracked job with an audit record of the erasure.

---

<a name="q27"></a>
## Q27. (Hard) How do you handle multi-region database replication conflict resolutions in Python?
**Answer:** Avoid conflicts by design (each record has one home region). When they happen: last-write-wins using timestamps/versions (simple, may lose data), field-level merge rules, or keeping conflicting versions for manual/business resolution. Use version columns and idempotent operations so conflicts can be detected and replayed.

---

<a name="q28"></a>
## Q28. (Hard) How would you configure PostgreSQL logical replication stream triggers in Django?
**Answer:** Logical replication is configured in PostgreSQL, not Django: create a publication for the tables (`CREATE PUBLICATION ... FOR TABLE ...`) via `RunSQL`, and a subscription on the target (or a CDC tool like Debezium reading the slot). Triggers on the subscriber must be enabled with `ALTER TABLE ... ENABLE REPLICA TRIGGER` to fire for replicated rows. Django just keeps writing normally.

---

<a name="q29"></a>
## Q29. (Hard) How would you implement CQRS write model to read model sync using CDC?
**Answer:** Writes go to normalized tables; a CDC tool (Debezium on the WAL) streams changes to a broker (Kafka/RabbitMQ); consumers update read models (denormalized tables, search index, cache). Consumers must be idempotent and handle ordering per key; expose that read models are eventually consistent.

---

<a name="q30"></a>
## Q30. (Hard) How do you prevent schema migration failures during automated blue-green deployments?
**Answer:** Both blue (old code) and green (new code) run against the **same** database, so migrations must work with both: expand-only migrations before the switch, contract migrations only after blue is retired. Test migrations in CI against a production-like DB, set `lock_timeout`, and never rename/drop columns the old version still uses.

---

<a name="q31"></a>
## Q31. (Hard) How do you configure Celery worker connection pools under serverless container scales?
**Answer:** When containers auto-scale, connections = containers × concurrency. Route all workers through PgBouncer/RDS Proxy, keep worker concurrency modest, close connections after tasks (`CONN_MAX_AGE = 0` or `close_old_connections()`), and set a max container count based on the DB's connection budget.

---

<a name="q32"></a>
## Q32. (Medium) How do you monitor database index read/write usage ratios to prune unused indexes?
**Answer:** Query `pg_stat_user_indexes` (`idx_scan`) together with table write counts (`n_tup_ins/upd/del` in `pg_stat_user_tables`) over a long enough period (include month-end jobs, replicas too). Indexes with zero or near-zero scans on write-heavy tables are candidates — check they don't enforce a constraint, then `DROP INDEX CONCURRENTLY`.

---

<a name="q33"></a>
## Q33. (Medium) How would you implement database-backed feature flags with tenant overrides?
**Answer:** Tables `Flag(name, default_enabled)` and `TenantFlag(tenant, flag, enabled)` with a unique pair. Resolve "tenant override → default" in one function, cache the result per tenant in Redis/in-memory with short TTL, and invalidate on change. Libraries like django-waffle cover the basics.

---

<a name="q34"></a>
## Q34. (Medium) How would you design a data retention pipeline that purges audit records?
**Answer:** Define retention per record type (legal requirements), partition audit tables by month, and have a scheduled job export expiring partitions to cold storage (if needed) and then drop them. Log every purge run. No row-by-row deletes on audit tables.

---

<a name="q35"></a>
## Q35. (Medium) How do you handle schema updates for database views mapped to Django models during deployments?
**Answer:** Views live in `RunSQL` migrations with unmanaged models. When an underlying table changes, recreate the view in the same migration (`CREATE OR REPLACE VIEW`, or drop + create), and keep the view's columns backward compatible with running code. For materialized views, recreate and refresh (concurrently) before switching code to new columns.
